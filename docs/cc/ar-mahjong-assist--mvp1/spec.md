# AR 麻将助手 MVP 产品规格

## 1. 定位

AR 麻将助手 MVP1 是一个以麻将场景为载体的 AR + CV 能力验证项目。它面向内部演示为主的普通用户，以广东麻将为默认规则，优先证明 RayNeo 眼镜可以在受控演示条件下完成图像采集、云端视觉识别、手牌/鸣牌结构化、基础手牌效率建议和低侵入展示。

本 MVP 不追求做成完整麻将游戏平台，也不承诺在缺少四家场况、牌河、宝牌等上下文时给出完整对局策略建议。麻将能力服务于 CV 技术积累和 AR 眼镜场景验证。规则扩展能力保留接口，但 MVP1 的验收优先围绕广东麻将。

## 2. 用户价值假设

- H1: 内部演示用户在真实眼镜链路中，可以在每轮出牌间隔内，也就是约 3-10 秒内，看到基于我方手牌/鸣牌的手牌效率建议。
- H2: MVP1 先记录识别置信度、建议置信度和 warning 字段，为后续低置信度交互做准备；专门的低置信度 UI/交互不进入本阶段。
- H3: AR 展示不会遮挡麻将牌面和核心视野，用户仍然能自然完成线下打牌动作。
- H4: MVP1 默认按广东麻将规则输出建议；四川麻将或其他规则通过受控规则配置接口接入，不影响广东麻将主路径验收。

## 3. MVP 包含

- 我方手牌识别。
- 吃、碰、杠等我方鸣牌识别。
- 手牌与鸣牌结构化组合。
- 多帧连续识别兜底。
- 基础牌效分析与手牌效率建议。
- 广东麻将默认规则配置。
- 规则扩展入口，允许内部用户上传受控的自定义规则配置，用于四川麻将或其他规则试验。
- 识别置信度、建议置信度和 warning 字段记录。
- 约 15 分钟连续一局可跑通。
- 眼镜端低侵入结果展示。
- 端到端耗时统计和失败样本回收。

## 4. MVP 不包含

- App 端或眼镜端模型部署。
- 语音交互和 STT 产品化链路。
- 专门的低置信度 UI/交互。
- 对外 QR 连接方案或生产鉴权方案。
- AI 对手建模。
- 四家完整追踪。
- 牌墙、宝牌、牌河识别。
- 完整对局策略建议。
- 胡牌提醒产品化。
- 面向外部用户的完整规则市场、规则编辑器或规则审核平台。
- 执行任意脚本形式的自定义规则上传。
- 新手教学。
- 战报、复盘、统计、云房间、观战、成就。
- 复杂 UI、主题化、情绪价值包装。
- 深度算番和复杂麻将游戏平台能力。

## 5. 核心用户流程

### 5.1 首次配置

1. 用户启动眼镜端应用。
2. 若本地没有连接配置，进入设置/扫码流程。
3. 用户扫描本地调试二维码。
4. 客户端解析 `serverUrl`、可选 `streamUrl`、`fps`、`sessionKey`、`label`。
5. 配置保存成功后进入运行态。

成功标准：内部开发/演示人员不需要手动改代码或输入 IP，就能切换本地调试后端环境。该二维码形式不作为对外用户连接方案。

### 5.2 开始对局

1. 客户端创建本地 `session_id`。
2. 客户端调用后端开始会话接口。
3. 进入持续采样或按当前配置的采样模式。
4. AR 展示进入低存在感运行态。

成功标准：会话开始失败时给出清晰状态，不静默进入假运行。

### 5.3 自动采集与建议

1. 眼镜端采集图片。
2. 客户端通过 HTTP 上传图片和 `session_id`。
3. 服务端识别手牌和鸣牌。
4. 服务端做结构化、多帧稳定判断和牌效建议。
5. 客户端显示手牌效率建议；置信度和 warning 字段先进入响应/日志记录，不要求 MVP1 实现专门低置信度 UI。
6. 若 WebSocket 可用，客户端接收建议/状态/警告下行。

成功标准：正常受控演示条件下用户能在 3-10 秒内看到可参考的手牌效率建议。

### 5.4 低置信度与重试

MVP1 不实现专门的低置信度交互。当前阶段只要求服务端/响应层保留识别置信度、建议置信度、`warning` 和 `is_stable` 等字段，供日志、QA 和后续 UI 迭代使用。

1. 如果识别不稳定、画面质量差、结构化异常或建议置信度不足，系统应记录对应原因。
2. 客户端仍按当前基础展示链路处理，不新增“重拍/隐藏/谨慎建议”等专门交互。
3. 失败样本应进入后续 QA/评测记录。

成功标准：MVP1 不把低置信度专门交互作为验收项，但必须保留后续实现所需的数据字段和样本记录。

### 5.5 WebSocket 降级

1. 如果 `streamUrl` 不存在或 WebSocket 断连，HTTP 分析响应仍可作为主链路。
2. UI 可显示流式通道不可用，但不应阻断 HTTP 成功结果展示。
3. 若 HTTP 成功但 WebSocket 失败，建议仍可展示，并带上降级状态。

成功标准：流式通道不是单点失败。

### 5.6 隐藏、刷新与结束

1. 用户可以通过 RayNeo touch action 或后续定义的交互隐藏建议、进入设置或结束会话。
2. 结束会话后客户端停止采样，服务端关闭或清理该 session 的活动状态。
3. 结束后不应继续展示过期建议。

成功标准：会话生命周期可控，不残留误导性 UI 或服务端状态。

## 6. AR 低侵入展示原则

- 默认 idle 态尽量少显示或不显示内容。
- 建议只在结果变化或用户需要时短暂展示。
- 不遮挡手牌、牌桌关键区域和用户自然视线。
- 文案短，优先显示建议牌，不展示长解释。
- 置信度等级和警告先作为数据字段记录；专门低置信度展示延后。
- 过期结果必须标记 stale 或隐藏。
- 错误状态要可恢复，不让用户困在不可解释的失败画面。

## 7. 验收标准

| 验收项 | MVP 标准 |
|---|---|
| 连续一局 | 约 15 分钟连续运行，能完成一局核心流程 |
| 整手牌识别 | 整手牌识别准确率目标 >80% |
| 鸣牌识别 | 我方手牌、吃、碰、杠不明显漏识别 |
| 多帧稳定 | 多帧后稳定性优于单帧 baseline |
| 响应耗时 | 端到端建议返回目标 3-10 秒 |
| 建议展示 | MVP1 展示手牌效率建议；识别置信度、建议置信度和 warning 至少进入响应或日志 |
| 错误建议 | 内部演示 provisional gate：演示样例中不出现明显错误建议；完整阈值进入 QA 阶段实测 |
| 人工纠正 | 内部演示 provisional gate：15 分钟演示流程中人工纠正次数目标不超过 2 次；完整阈值进入 QA 阶段实测 |
| 低侵入体验 | 不遮挡视野，不干扰正常打牌动作 |
| 规则主路径 | 默认广东麻将规则可用于内部演示；自定义规则配置不阻断广东麻将验收 |

## 8. 首个产品验证门槛

阶段 2 文档收敛完成后，后续第一批 `cc-work` 代码任务应优先验证真实用户价值：

```text
实机采集 -> 服务端识别 -> 手牌效率建议返回 -> AR 低侵入展示 -> 置信度/warning 可记录
```

如果这个链路不能稳定证明价值，应优先修链路、评测和反馈闭环，而不是继续扩展功能。

## 9. 待产品确认问题

- RayNeo touch action 在 MVP 中承担哪些动作：隐藏、重试、暂停、结束，还是仅保留调试入口？
- QA 阶段是否需要把 provisional gate 升级为正式错误建议率和人工纠正次数阈值？
- 自定义规则配置第一版采用 JSON、YAML 还是后端管理接口？
- 四川麻将等自定义规则进入 MVP1 演示范围，还是只作为接口可用性验证？

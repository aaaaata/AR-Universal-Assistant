## 0. 文档定位

本文是技术方案设计，不重复项目规划和项目管理。

- 规划文档：项目目标、MVP 边界、产品取舍。
- 管理文档：节奏、分工、风险、验收闭环。
- 本文：技术链路、方案候选、验证方法、接口草案、性能拆解、当前代码迁移。

当前阶段不拍死所有技术参数。本文采用：

```text

```

## 1. 当前技术结论

已确定：

- 云端服务承载主要计算。
- App / 眼镜保持轻端。
- App 端模型部署暂不进入 MVP。
- 本地 Python 只作为开发调试，不作为产品路径。
- CV 识别是主路径风险。
- 多帧连续性进入 MVP 兜底方案。
- 建议输出必须带识别置信度和建议置信度。

未确定：

- 最终 YOLO 模型版本。
- 是否需要重训模型。
- 单次分析采集几帧。
- 多帧采用投票、最优帧，还是混合策略。
- 图片上传使用 base64 还是对象存储 URL。
- 低置信度阈值。
- 端到端响应耗时各环节预算。

本阶段目标：用离线评测和小规模实测拿结论，不靠主观判断定方案。

## 2. 总体技术链路

```text
AR 眼镜端
  图像采集
  低侵入展示
  连接保持

App / 通用入口
  会话建立
  参数配置
  图片转发
  结果消费

云端服务
  图像质量检查
  YOLO 检测
  区域归类
  手牌 / 鸣牌结构化
  多帧稳定性判断
  牌效分析
  建议生成
  置信度输出

评测体系
  标准图片集
  连续帧序列
  标注数据
  指标统计
  错误样本库
```

端到端顺序：

1. App / 眼镜创建会话。
2. 眼镜采集单帧或短序列。
3. App 上传图片到云端。
4. 云端完成单帧识别。
5. 云端组合手牌 / 鸣牌。
6. 云端做多帧稳定性判断。
7. 稳定结果进入建议服务。
8. 云端返回建议、置信度、展示提示。
9. App / 眼镜展示结果。
10. 云端记录耗时、错误、低置信度原因。

## 3. 视觉模型方案

### 3.1 当前基线

本地代码已有 ONNX YOLO 推理链路。当前版本可用于 Demo，但不能直接证明产品链路成立。

当前基线要补齐 3 类数据：

- 准确率：整手牌、单牌、吃碰杠。
- 稳定性：连续帧波动、漏检、误检。
- 耗时：模型推理耗时、端到端耗时。

### 3.2 候选方案

| 方案 | 说明 | 优点 | 风险 | 适用判断 |
|---|---|---|---|---|
| A. 沿用当前 ONNX YOLO | 先用现有模型跑 baseline | 成本低，最快有数据 | 准确率可能不足 | W2 必跑 |
| B. 轻量 YOLO 重训 | 小模型，云端推理快 | 耗时可控，迭代快 | 小牌和易混牌可能不够准 | baseline 不达标但耗时敏感 |
| C. 中等 YOLO 重训 | 模型更强 | 准确率上限更高 | 推理慢，成本高 | 轻量模型准确率不足 |
| D. 检测 + 二次分类 | YOLO 先定位，分类器细分牌面 | 易混牌可能更好 | 链路复杂，训练成本高 | 易混牌长期卡住时兜底 |

### 3.3 选择依据

不先定模型名。先用同一批评测集比较：

- 整手牌识别准确率
- 单牌准确率
- 漏检率
- 误检率
- 易混牌错误率
- 推理耗时 P95
- 重训成本
- 部署复杂度

### 3.4 阶段判断标准

| 阶段 | 目标 | 结论动作 |
|---|---|---|
| W2 | 跑出现有模型 baseline | 判断是否能继续沿用 |
| W3 | 手牌识别专项评测 | 判断是否需要重训 |
| W4 | 吃碰杠结构化评测 | 判断是否增加区域模型或规则 |
| W5 | 多帧前后对比 | 判断单模型是否够用 |

### 3.5 暂定策略

MVP 先走 A，再根据数据决定 B / C。D 只作为后备，不提前投入。

## 4. 数据集与标注方案

### 4.1 数据集目标

数据集不是资料沉淀，是模型选择和方案判断依据。

最小数据集必须覆盖：

- 我方整手牌。
- 吃 / 碰 / 杠。
- 站立牌。
- 倒立牌。
- 不同距离。
- 不同倾斜角度。
- 弱光。
- 反光。
- 手部遮挡。
- 连续帧序列。
- 失败样本。

### 4.2 标注粒度

单牌标注：

```json
{
  "tile": "5万",
  "bbox": [120, 240, 168, 310],
  "pose": "standing",
  "region": "hand",
  "occluded": false
}
```

区域标注：

```json
{
  "region": "meld",
  "type": "peng",
  "tiles": ["9条", "9条", "9条"]
}
```

### 4.3 数据版本

数据集需要版本号。

```text
dataset_v0.1
  标准手牌
  吃碰杠
  连续帧
  失败样本
  标注文件
  评测报告
```

每次模型评测必须记录：

- 数据集版本。
- 模型版本。
- 推理配置。
- 指标结果。
- 错误样本索引。

## 5. 手牌 / 鸣牌结构化方案

### 5.1 问题定义

YOLO 输出的是单张牌检测结果。建议服务需要的是结构化牌组。

需要完成：

```text
单牌检测结果
  组合为
手牌列表 + 鸣牌列表 + 异常状态
```

### 5.2 MVP 输出结构

```json
{
  "hand_tiles": ["1万", "2万", "3万"],
  "meld_tiles": [
    {
      "type": "peng",
      "tiles": ["9条", "9条", "9条"]
    }
  ],
  "structure_status": "normal",
  "structure_confidence": 0.82
}
```

### 5.3 结构化策略

优先使用轻量规则：

- 按 bbox 位置聚类。
- 按牌面朝向和排列间距判断区域。
- 手牌区域和鸣牌区域分开排序。
- 吃 / 碰 / 杠先用数量和排列形态判断。
- 异常情况只降置信度，不直接中断。

### 5.4 异常类型

| 异常 | 处理 |
|---|---|
| 手牌数量异常 | 降低识别置信度 |
| 鸣牌数量异常 | 标记 `meld_uncertain` |
| 单牌重复框 | 做 NMS 或合并 |
| 关键牌漏检 | 标记低置信度 |
| 区域不确定 | 标记 `region_uncertain` |

### 5.5 待验证问题

- 只靠 bbox 规则能否稳定区分手牌和鸣牌。
- 吃 / 碰 / 杠是否需要独立区域检测。
- 倾斜视角下排序是否稳定。
- 结构化错误对建议影响多大。

## 6. 多帧连续识别方案

### 6.1 目标

多帧不是为了变复杂，是为了给单帧识别兜底。

解决：

- 偶发漏检。
- 偶发误检。
- 手部遮挡。
- 取景轻微抖动。
- 单帧置信度波动。

### 6.2 初始方案

MVP 先采用短序列方案：

- 单次分析采集 3-5 帧。
- 每帧独立识别。
- 对多帧牌面集合做一致性统计。
- 对区域结果做一致性统计。
- 输出稳定牌组和识别置信度。

### 6.3 三种候选策略

| 策略 | 说明 | 优点 | 风险 | 使用阶段 |
|---|---|---|---|---|
| 多数投票 | 多帧中出现次数多的牌保留 | 简单，易实现 | 连续漏检时失效 | MVP 首选 |
| 最优帧选择 | 选质量最高、置信度最高的一帧 | 快，结果完整 | 单帧误判仍可能保留 | MVP 备选 |
| 混合策略 | 先选优质帧，再用投票修正 | 稳定性更好 | 实现稍复杂 | W5 后判断 |

### 6.4 初始判断逻辑

```text
输入 3-5 帧识别结果
统计每张牌出现次数
统计每个区域识别一致性
检查手牌 / 鸣牌结构是否合法
计算识别置信度
输出稳定结果或低置信度结果
```

### 6.5 稳定条件

可先使用宽松规则，后续用数据调阈值：

- 手牌数量合理。
- 核心牌面在多数帧出现。
- 区域归类基本一致。
- 图像质量不是连续低分。
- 结构化异常不严重。

### 6.6 低置信度处理

低置信度不等于无建议。

返回：

```json
{
  "is_stable": false,
  "recognition_confidence": 0.54,
  "low_confidence_reason": "multi_frame_inconsistent",
  "ui_hint": {
    "level": "warning",
    "text": "识别不稳，建议谨慎参考"
  }
}
```

### 6.7 待验证问题

- 3 帧是否够。
- 5 帧是否太慢。
- 投票是否优于最优帧。
- 多帧能否明显降低漏检率。
- 多帧是否引入更高延迟。

## 7. 置信度方案

### 7.1 识别置信度

识别置信度由 4 类因素组成：

| 因素 | 作用 |
|---|---|
| 模型置信度 | 单牌检测和分类可信度 |
| 帧间一致性 | 多帧是否稳定 |
| 结构合法性 | 手牌 / 鸣牌组合是否合理 |
| 图像质量 | 模糊、遮挡、反光、距离 |

初期不写死公式。先记录 4 类分数，再用实测数据调整权重。

### 7.2 建议置信度

建议置信度不等于识别置信度。

建议置信度受 3 件事影响：

- 输入牌组是否可信。
- 候选出牌差距是否明显。
- 当前规则引擎是否能覆盖该牌型。

示例：

```json
{
  "recognition_confidence": 0.86,
  "suggestion_confidence": 0.72,
  "confidence_level": "medium"
}
```

### 7.3 展示分级

| 等级 | 条件 | 展示 |
|---|---|---|
| 高 | 识别稳定，建议差距明显 | 直接展示建议 |
| 中 | 识别基本稳定，建议可参考 | 展示建议和可信度 |
| 低 | 识别波动或结构异常 | 提示谨慎参考 |
| 重拍 | 画面质量差或结果严重异常 | 建议重拍 |

## 8. 耗时链路与优化方案

### 8.1 耗时拆分

端到端耗时需要拆开统计：

| 环节 | 说明 |
|---|---|
| 采集耗时 | 眼镜拍照或取帧 |
| 压缩耗时 | 图片缩放、JPEG 压缩 |
| 上传耗时 | App 到云端 |
| 排队耗时 | 云端请求等待 |
| 推理耗时 | YOLO 模型执行 |
| 后处理耗时 | NMS、区域归类、结构化 |
| 多帧耗时 | 多帧对齐和一致性计算 |
| 建议耗时 | 牌效分析和建议生成 |
| 返回耗时 | 云端返回到端侧展示 |

### 8.2 MVP 优化优先级

优先做：

1. 控制图片尺寸。
2. 控制 JPEG 质量。
3. 控制单次帧数。
4. 记录每环节耗时。
5. 模型推理耗时对比。
6. 云端接口减少无用字段。

暂不做：

- App 端模型推理。
- 大规模并发优化。
- 复杂缓存系统。
- 极致端侧性能优化。

### 8.3 初始目标

MVP 响应目标：3-10 秒内返回建议。

更细目标先不拍死。W2/W3 拿 baseline 后再拆预算。

必须记录：

```json
{
  "latency": {
    "capture_ms": 300,
    "upload_ms": 800,
    "inference_ms": 1200,
    "postprocess_ms": 120,
    "suggestion_ms": 50,
    "total_ms": 3200
  }
}
```

### 8.4 判断标准

- P95 总耗时满足出牌节奏。
- 增加多帧后，准确率收益大于耗时损失。
- 如果 5 帧过慢，降到 3 帧。
- 如果上传慢，优先压缩图片，不改端侧推理方向。

## 10. 前端展示协议

前端只关心状态，不理解复杂策略。

| 状态 | 含义 | 展示 |
|---|---|---|
| `normal` | 识别稳定，建议可用 | 建议打 9条 |
| `warning` | 可参考，但不稳定 | 识别不稳，谨慎参考 |
| `retry` | 图像质量差 | 建议重拍 |
| `error` | 服务或连接异常 | 连接异常 / 分析失败 |

展示原则：

- 少字。
- 不遮挡视野。
- 不解释长策略。
- 可显示可信度等级，不强行显示小数。

| 多帧对比报告 | 判断多帧是否有效 |
| P95 耗时报告 | 判断是否满足出牌节奏 |

### 11.3 关键指标

- 整手牌识别准确率。
- 单牌准确率。
- 漏检率。
- 误检率。
- 手牌 / 鸣牌区域准确率。
- 多帧后稳定性提升。
- 端到端响应耗时 P95。

## 15. 也哥口径自评

通过项：

- 技术主路清楚：云端 + 轻端。
- 没有把 App 端模型部署拉回 MVP。
- CV 识别、数据集、离线评测是第一优先级。
- 多帧连续性写成 MVP 兜底，不是远期优化。
- 麻将规则和建议模块被限制为轻量能力。

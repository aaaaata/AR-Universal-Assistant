# AR 麻将助手 MVP 项目管理文档

更新时间：2026-07-23  
当前阶段：Q3 MVP 阶段  
项目规模：1 名正式成员 + 1 名实习生  
管理口径：按周解锁关键能力，先离线验证，再实机联调

---

## 1. 项目总览

### 项目定位

本项目以麻将场景为载体，验证 AR 眼镜图像采集、复杂桌面物体识别、手牌/鸣牌结构化理解、多帧连续识别稳定性、结果低侵入展示，以及云端服务 + 轻端入口的 CV 应用链路。

麻将能力服务于 CV 技术积累，不以完整麻将游戏平台为目标。

核心链路：

```text
眼镜图像采集 -> 云端视觉识别 -> 手牌/鸣牌结构化 -> 多帧稳定判断 -> 牌效/建议 -> 轻端结果展示
```

### 已确认方向

- 产品方案以云端服务为主。
- App / 眼镜保持轻端和通用入口。
- App 端暂不承载模型推理。
- 本地 Python 服务仅用于开发调试，不进入产品路径。
- MVP 聚焦视觉识别、结构化理解、基础建议与连续一局可用。
- 不追求复杂麻将玩法、游戏平台化功能、复杂 UI 或语音交互。
- 多帧连续性作为 MVP 识别兜底机制。

### 当前管理判断

Q3 做完 MVP 仍有机会，但成立前提已经变化：

- 主路径变成云端服务能力、离线评测体系和实机连续一局验证。
- 联调不是最难点，最难点是识别能力、数据集、评测体系、结构化理解和多帧稳定性机制。
- 10 月目标是形成可演示 / 可试用版本，不按半人年或一人年的完整产品项目推进。
- MVP 后续投入必须基于实测数据决定，不默认进入长期打磨。

当前最大风险：

- 标准图片集 / 视频序列不足，导致准确率无法稳定评估。
- 单帧识别波动大，影响建议可靠性。
- 手牌、鸣牌、牌桌区域结构化能力不足。
- 云端链路响应耗时或网络稳定性影响用户体验。
- 1 名正式成员 + 1 名实习生资源有限，不能同时深做端侧、复杂 UI、深度规则和完整牌局状态。

### 技术投入优先级

| 优先级 | 方向 | 管理口径 |
|---|---|---|
| P0 | YOLO 重训、训练集、离线准确率评测 | 核心 CV 能力，优先投入 |
| P0 | 手牌 / 鸣牌结构化组合 | MVP 必须闭环，最低要求是我方手牌和吃碰杠识别不漏 |
| P1 | 多帧连续性和置信度 | 作为识别兜底机制，提升稳定性 |
| P2 | 轻量牌效建议 | 只支撑 MVP 建议展示，投入不超过 1 人周 |
| 不投入 | 复杂 UI、深度算番、游戏平台能力 | ROI 不合适，避免发散 |

## 2. MVP 范围与验收标准

### MVP 包含

- 我方手牌识别
- 吃 / 碰 / 杠等鸣牌识别
- 手牌与鸣牌结构化组合
- 多帧连续识别兜底
- 基础牌效分析
- 出牌建议
- 胡牌提醒
- 识别置信度 + 建议置信度展示
- 约 15 分钟连续一局可跑通

### MVP 暂不包含

- App 端模型部署
- 语音交互
- AI 对手建模
- 四家完整追踪
- 牌墙、宝牌、牌河识别
- 新手教学
- 战报、复盘、统计
- 复杂 UI、云房间、观战、成就
- 深度算番和复杂麻将游戏平台能力

### 牌局管理口径

MVP 只保留支撑连续一局所需的最小状态，不追求完整牌局历史。

完整牌局管理作为 P2，只有在手牌、鸣牌和多帧稳定性机制达到可用后再扩展。

### MVP 验收标准

| 验收项 | 标准 |
|---|---|
| 连续一局 | 能连续打完一局，目标约 15 分钟 |
| 整手牌识别 | 整手牌识别准确率 >80% |
| 鸣牌识别 | 我方手牌、吃 / 碰 / 杠不明显漏识别 |
| 多帧兜底 | 多帧连续判断后，识别稳定性优于单帧 baseline |
| 建议输出 | 每次建议展示识别置信度和建议置信度 |
| 低置信度体验 | 提示谨慎参考或建议重拍 |
| 响应耗时 | 满足每轮出牌间隔，目标 3~10 秒内完成 |
| 人工纠正 | 记录一局内人工纠正次数，并根据实测确定上限 |
| 错误建议 | 记录错误建议率，并根据实测确定可接受阈值 |

### 出牌建议质量口径

“有建议优先于无建议”作为产品输出策略保留，但不能脱离置信度单独使用。

建议输出必须包含：

- 推荐出牌
- 识别置信度
- 建议置信度
- 低置信度提示

示例：

```text
推荐：切 8万
识别置信度：82%
建议置信度：68%
提示：识别较稳定，仅供参考
```

## 3. 外部依赖与对齐事项

### 连接层与数据消费模式

连接层和数据消费模式需要保持通用性，避免做成麻将专用链路。

| 事项 | 管理要求 |
|---|---|
| 目标 | App / 眼镜作为通用入口，后续扑克、做菜等 CV 场景可复用同一模式 |
| 依赖方 | 肖长建负责抽象定义连接层和数据消费模式 |
| W2 前需确认 | 数据上传、结果消费、错误状态、低置信度提示的基础接口口径 |
| 未闭环风险 | 若接口口径未确认，云端服务可按临时协议推进，但后续存在返工风险 |

### 责任边界

- 正式成员对技术方案、范围判断、关键结论和对外同步负责。
- 实习生对数据采集、测试记录、问题复现和初步统计负责。
- 关键节点的最终结论不能只写参与人，必须明确由正式成员确认。

## 4. 周推进计划

### 推进原则

- 每周解锁一个关键能力，不平均用力。
- 先离线能力验证，再实机联调。
- 每周必须有可验证输出物。
- 联调放在能力稳定后，不作为前期主要工作。
- 每周基于实测数据决定下一周范围。

### Q3 MVP 周计划

| 周期 | 解锁目标 | 交付物 | 负责人 |
|---|---|---|---|
| W1：7/23 - 7/24 | 项目方向规划、项目管理及方案设计输出 | 项目规划文档优化版、项目管理文档、方案设计文档 | 正式成员 |
| W2：7/27 - 7/31 | 明确云服务主路径框架设计和离线评测方法 | 云端服务接口/数据结构草案、图片采集规范、样本标签规范、X3 实拍标准图片集、至少一组连续图片/视频序列、离线准确率统计脚本、初版 baseline 数据 | 正式成员对结论负责，实习生负责采集和统计 |
| W3：8/3 - 8/7 | 提升我方手牌识别能力 | 手牌识别 baseline、整手牌准确率统计 | 实习生主测，正式成员评审 |
| W4：8/10 - 8/14 | 建立多帧连续性和置信度机制 | 多帧稳定判断、识别置信度、低置信度提示 | 正式成员 |
| W5：8/17 - 8/21 | 提升 MVP 必需区域识别能力 | 我方手牌区、副露/吃碰杠区域划分设计，区域识别准确率统计；牌池/牌河/牌墙只做样本观察，不作为交付 | 实习生主测，正式成员设计 |
| W6：8/24 - 8/28 | 解决吃 / 碰 / 杠鸣牌识别 | 手牌 + 鸣牌结构化输出 | 正式成员 + 实习生 |
| W7：8/31 - 9/4 | 接入轻量牌效和建议能力 | 建议结果、建议置信度、错误案例记录 | 正式成员 |
| W8：9/7 - 9/11 | 实机连续一局验证 | 15 分钟连续牌局测试、卡顿/错误/纠正次数统计 | 正式成员 + 实习生 |
| W9：9/14 - 9/18 | MVP 收敛和问题修复 | 阻断问题关闭、已知问题清单、0.1.0 候选版本 | 正式成员 |

### W2 范围控制

W2 必须闭环：

- X3 实拍标准图片集。
- 至少一组连续图片/视频序列。
- 离线准确率统计脚本。
- 样本标签规范。
- 初版 baseline 数据。
- 云端服务接口/数据结构草案。

W2 不追求：

- 完整自动化回归平台。
- 大规模数据集。
- 完整云端工程化部署。

### 本周必须关闭

- 优化版项目规划文档是否已体现云端主路径。
- 项目管理文档是否与优化版规划及王也评论一致。
- 方案设计文档是否能支撑 W2 的云端服务框架和评测体系建设。
- W2 标准图片/视频采集规范是否清楚。
- 肖长建侧连接层和数据消费模式是否已有初步对齐计划。

## 5. 测试验证体系

### 验证对象与指标

| 验证对象 | 验证方式 | 主要指标 |
|---|---|---|
| 标准图片集 | 固定样本离线回归 | 整手牌准确率、漏检率、误检率 |
| 视频 / 图片序列 | 模拟连续识别链路 | 多帧稳定性、帧间一致性 |
| 实物麻将实测 | X3 采集真实桌面画面 | 距离、角度、弱光、反光、竖起/躺倒鲁棒性 |
| MVP 必需区域识别 | 区分我方手牌区、副露/吃碰杠区域 | 区域划分准确率、区域内识别准确率 |
| 连续一局测试 | 约 15 分钟完整流程 | 卡顿次数、人工纠正次数、响应耗时 |
| 问题案例库 | 沉淀异常样本并回归 | 复现能力、修复闭环 |

### 离线评测要求

W2 开始建立离线评测体系，避免长期依赖实机反复试。

最小要求：

- 标准图片集按场景分类：距离、角度、光照、反光、遮挡、站立牌、倒立牌。
- 视频/图片序列覆盖连续识别场景。
- 每次模型或规则调整后能复跑准确率统计。
- 问题案例能进入回归集。

### 多帧连续性测试

记录项：

- 单帧识别结果
- 多帧聚合结果
- 帧间一致性
- 识别置信度
- 是否触发低置信度提示
- 多帧结果是否优于单帧 baseline

结论口径：

```text
有效 / 有条件有效 / 无明显收益
```

### 端到端耗时测试

统计项：

- 拍照耗时
- 图片压缩/上传耗时
- 云端识别耗时
- 多帧稳定判断耗时
- 牌效建议耗时
- 结果展示耗时
- 端到端总耗时

输出：平均值、最大值、P95。

## 6. 风险与决策跟踪

### 当前关键风险

| 风险 | 影响 | 应对 |
|---|---|---|
| 离线评测集不足 | 无法判断识别优化是否有效 | W2 必须产出标准图片集、连续序列和初版 baseline |
| 连接层/数据消费模式未对齐 | 后续通用入口可能返工 | W2 前与肖长建对齐接口口径，必要时先按临时协议推进 |
| 云端链路依赖网络 | 可能影响实时性和稳定性 | W2 起统计端到端耗时，低置信度或超时给提示 |
| 识别准确率不足 | 直接影响建议可靠性 | 重训模型、扩充数据集、建立离线回归 |
| 单帧结果波动 | 建议输出不稳定 | 引入多帧连续性和置信度机制 |
| MVP 必需区域划分不足 | 手牌、鸣牌容易混淆 | W5 只聚焦我方手牌区和副露/吃碰杠区域 |
| 实机调试效率低 | 问题难复现、推进慢 | 提前建设标准图片/视频序列和问题案例库 |
| 人力有限 | 多线并行容易失控 | 聚焦云端主路径和 CV 能力，复杂功能延期 |

### 已确认决策

| 时间 | 决策 |
|---|---|
| 前期 | MVP 先去掉语音交互，聚焦视觉可用 |
| 上周 | MVP 验收目标为连续完整一局，约 15 分钟 |
| 上周 | 整手牌识别准确率目标 >80% |
| 上周 | 有建议优先于无建议，但必须伴随识别置信度和建议置信度 |
| 2026-07-23 | 项目定位调整为以麻将为载体的 CV 能力验证项目 |
| 2026-07-23 | 产品方案以云端服务为主 |
| 2026-07-23 | App 端暂不承载模型推理 |
| 2026-07-23 | 多帧连续性作为 MVP 识别兜底机制 |
| 2026-07-23 | 按周解锁关键能力，不急于联调 |
| 2026-07-23 | 客户端需作为通用入口，连接层和数据消费模式需抽象设计 |
| 2026-07-23 | 牌效/麻将规则只做轻量投入，不超过 1 人周 |
| 2026-07-23 | 10 月目标形成可演示 / 可试用版本，不做长期大而全打磨 |

### 待实测后补齐

- 整手牌准确率基线。
- 鸣牌识别准确率基线。
- 多帧相比单帧的收益。
- 端到端响应耗时 P95。
- 错误建议率统计口径和可接受阈值。
- 一局内人工纠正次数上限。

## 7. 周会与记录模板

### 周会关注点

每周只看四件事：

1. 本周解锁目标是否完成。
2. 是否有可验证输出物。
3. 数据是否支持进入下一周目标。
4. 是否需要缩范围或调整优先级。

### 周进展记录模板

```text
需要调整的范围：

```
